## 一、一句话结论

**多资产（ETF 袖套）这条研究线可以结项了。**

14 个实验把「资产侧 + 组合侧」能想到的分支基本探完：
**唯一的改进（剔除可转债 ETF）是分类修正，不是技巧**；
其余全部被证伪或被证明「不可识别」。
而且决定性的证据不是「过去版本输了」，而是**「上界增益跨窗口都很小」**——
即使完美知道未来 252 天的分布，袖套内部的权重选择在 5 个窗口里
只能带来 **≤ +0.48** 的组合夏普增益，其中 **3 个窗口 ≤ +0.14**，
w2013 的上界**比定稿还低**（−0.0257）。

**资源应该转向 A 股腿**：组合 **57.5% 的方差在那里**（P13 §结论），
而 A 股腿这条线（P7/P8/P9/P10/P11）**还没结项** —— 它只被"减法"（消融/中性化/降频）探过，
**从来没有"换信号源"**。

## 五、结项判断

**多资产（ETF 袖套）线：结项（P17 后为彻底结项）。**
- 未探分支 #1（类内选标的）/ #2（袖套调仓频率）**已由 P17 一次性收掉并封线**；
- 剩余 #3（组合层 vol-target）/ #4（commodity 拆分）的期望信息量都**低于已探分支被封时的水平**，
  且 #3 已有项目内规律直接判死（vol-target 对已集中的组合是净亏损）、#4 与已证伪形态同源；
- → **多资产线不再有值得做的分支。资源全部转 A 股腿。**

**A 股腿线：继续，且优先级高于一切。**
- 已探：因子层（P7 ❌）、暴露层（P8 ❌）、执行层（P9 ⚠️）、基准口径（P11 ✅）、
  长历史数据（P10 ✅）、选股层 alpha 存在性（P11 ✅ α 5/5 为正）。
- **未探：换信号源**（分支 #5）。这是 P11 结论指向的地方 ——
  α 稳定为正说明**信号有信息量**，但信息量就到此为止；继续在 25f 里做加减法已经没有空间。
- **2026-11-01 更新**：换源**预筛选**已完成（§八）——8 个现成候选全部证伪；
  更根本的是 **DSR/PBO 给出了结构性封线**：项目累计 **1937** 次试验（1070 历史 + P17 的 867）
  → 零假设期望最大夏普 **SR0 = 2.35**（⚠️ SR0 不是显著性门槛；要 DSR ≥ 0.95 需夏普 ≥ **3.88**），
  而定稿 honest_composite 0.8796 校正后 **DSR=0.0075、pass_95=false**，
  策略间排序 **PBO=0.5075 ≈ 抛硬币**。
  → **「继续加试验」的期望收益为负**（n_trials 上升、DSR 阈值上升、真实 alpha 不变）。
  → 换源若要做，唯一站得住的形式是**用先验（信号正交性）限定搜索空间，把 n_trials 压到 <10**，
  再在 DSR 下重估；否则只是把过拟合从 1070 次做到 1071 次。

## 六、这一轮沉淀的通用铁律

1. **先算 Oracle 上界，再设计优化器。** `oracle − 可实现` 的差 = 未来信息量的量级。
   差很小 → 这条路没有空间，调参只是在拟合噪声。
2. **只赢夏普不算赢。** 判据必须同时含**绝对收益下限**与**波动下限**，
   否则"用收益换波动"会被当成"改进"（P15：夏普 +0.75，σ 只剩 66.8%）。
3. **同一套撮合逻辑只能有一份实现。** 复制出去的那份一定会漂移
   （P15 自带副本 vs P12：`0.7780` vs `0.7727`）→ 跨脚本必须 `import` 同一个函数。
4. **撮合器必须有"目标权重是否真的达成"的独立验证。**
   审计器只核「文档 vs 产物」，不核「产物是用哪个实现算的」——
   P12 长历史数字与产物完全一致、审计全绿，但整个样本建立在"类间等权从未发生"的撮合器上。
5. **文档表格用生成器渲染；回填器只用于纯数值格。**
   `backfill --apply` 会毁掉复合单元格（`10/20 = 50%` → `55/20 = 50%`），
   而它看着"合理"。审计器与回填器取值不一致时，**以直接读产物 JSON 为准**。
6. **新增表格一律放文末附录。** 审计器按「表序号」定位，插表会打乱后面所有锚点。
7. **结论方向与精确数字要分开验证。** 撮合器修复后 P12 数字变了 ±0.04，
   但定性结论（α 3/3 为正）纹丝不动 → 修撮合器后要重跑**并重新核对结论方向**，
   不能只看数字变没变。
8. **引用任何策略夏普前，先声明 lag 口径。**
   lag0（用当日收盘价算信号、当日成交）= 未来函数。实测 `gbm_voltgt`：
   **lag0 报 1.155 / OOS 1.018，真实盘 lag1 只有 0.5258** —— 差 0.63 全是未来函数。
   项目里已登记为正式策略的 `gbm_voltgt`（付费档）**其 1.155 不可用于任何比较**。
9. **做下一个试验前，先看 DSR / PBO**（`data/backtest/deflated_sharpe.json`）。
   项目累计 **n_trials = 1070**（P17 后 **1937**）→ 零假设期望最大夏普 **SR0 = 2.2562**
   （⚠️ **SR0 ≠ 显著性门槛**；要让 DSR ≥ 0.95，实际夏普需 ≥ **3.74 / 3.88**）；
   定稿 honest_composite 0.8796 校正后 **DSR = 0.01133、pass_95 = false**；
   **PBO = 0.5075 ≈ 抛硬币**。
   → **n_trials 上升 = DSR 阈值上升 = 结论只会更差**。
   → 任何新试验必须**先用先验把搜索空间压小**（例如只保留正交性有证据支撑的组合），
   否则只是把过拟合从 1070 次做到 1071 次。
   → 另：`days_needed_for_95pct` 显示夏普 1.5 需 4000 天（11 年）→ **3 年窗口统计上什么都证明不了**。

## 十、P18 预注册：42f 之上叠加 gbm 增量（2026-11-01，跑之前落纸）

**依据**：§八.3 —— 全部证据里唯一指向「换源有空间」的支点是 **gbm ↔ 量价 rank IC 0.112 / 0.150（近乎正交）**。
其余 7 个候选全灭。故只做**增量叠加**（不是替换），且必须把试验数压到 <10。

### 10.1 事前固定的搜索空间（**不可事后扩**）

| 项 | 事前取值（唯一） |
|---|---|
| 融合方式 | **截面 z-score 后线性加权**（不扫其他方式） |
| 融合权重 `w_gbm` | **{0.10, 0.20, 0.30, 0.50}** + 基线 `0.00` = **5 个臂** |
| gbm 的 vol-target | **关闭**（只取排序信息，仓位由 42f 侧定） |
| lag | 1（与定稿一致） |
| 调仓频率 | 周频（周五信号 → 周一执行，与定稿一致） |
| 42f 因子集 | 定稿 25 公式版（`use_panel=False`） |
| **n_trials** | **5**（用 `trial_budget.py --register --override --trials 5` 覆盖全局 1937） |

**理由**：搜索空间由「先验」而非「结果」决定 —— 4 个权重是**有序网格**（0.1→0.5），
不是自由搜索；gbm 权重越高越可能拉低（gbm 单腿真实盘 lag1 仅 **0.5258**，
源 `data/backtest/gbm_lag1.json`），故网格**单调向下加密**。

### 10.2 事前固定的判据（全过才算「提升」）

| 判据 | 阈值 |
|---|---|
| (a) main 组合夏普 | ≥ 基线 **+ 0.05** |
| (b) oos 组合夏普 | ≥ 基线 **− 0.02** |
| (c) placebo 随机对照 | 规则臂夏普 > 同参数随机分数臂夏普（**随机必须被击败**） |
| (d) 滚动 504 日夏普胜率 | ≥ 60% |
| (e) DSR（override 后 n_trials=5） | ~~DSR ≥ 0.95~~ → **降级为报告项**（见下方说明） |
| (f) 跨窗口迁移 | oos 最优权重在 main 不得排最差（**不得反向**） |

**⚠️ (e) 降级说明（2026-11-01，正式跑之前修正）**：
冒烟实测发现 `n_trials=5` 的实验口径门槛 = **2.1964**，而定稿组合夏普只有 **1.4114** →
**任何臂都不可能达到 DSR ≥ 0.95** → 把 (e) 当否决条件 = 实验无论结果如何都判死 = 零信息量。
故 (e) 降级为**证据强度报告项**（如实报 DSR 值与门槛），不参与通过判定。
**通过判定 = (a)(b)(c)(d)(f) 五条全过。**
此修正发生在**正式跑之前**（冒烟不算正式运行），不构成事后放宽。

**否决前置**：若 42f 与 gbm 分数的**同日截面相关系数 > 0.3**（说明正交性在同日不成立），
→ **不跑融合回测**，直接判死。（此判据本身也要落进产物）

### 10.3 实现要点（已勘察源码，坑先写下来）

- gbm 的 `_gbm_voltgt_scores` 存的是 **LightGBM 原始预测值**（非 z-score），
  且**键 = 信号日**（lag 在 `generate_signals` 里做）→ 融合前必须
  **① 沿交易日历右移 1 个交易日**（键=执行日）**② 当日截面 z-score**。
  42f 的 `_honest_composite_scores` 键**已是执行日**（`lagged[t]=composite[t-1]`）。
- gbm 内嵌 **vol-target 会按波动率砍持仓数** → 融合时必须**关闭**，
  否则 gbm 的分数集合随波动率变化，融合变成「两个不同股票池的拼接」。
- 42f 与 gbm 各跑一次 prepare 后**缓存**，5 个臂复用（否则 5×gbm 训练 ≈ 数小时）。
  缓存用 **日期×代码矩阵**（5513×750×float64 ≈ 33MB/路），**不要用 per-stock dict**
  （4M 条 dict entry → 内存爆 + 融合慢）。
- **模块全局污染**：42f 的 `_HONEST_FORMULAS` 与 gbm 的因子表都是模块级全局，
  每臂结束必须还原并断言（沿用 P7 的 `BASE_SIGNS` 硬断言）。

### 10.4 结论口径

无论通过与否，**这一轮只回答一个问题**：「gbm 的正交信息能不能通过分数级融合
给 42f 带来增量」。若 (a)~(f) 任一不过 → 换源线**彻底封线**，
资源转向**商业化交付**（当前定稿 main 1.4114 / oos 1.0691 即为最终版本）。

### 11.4 两条比"判否"更重要的事实

**(1) 全场最高分臂是安慰剂，不是规则臂。**
`plc_w0.10_s7` = **1.4657** > 基线 1.4114 > 全部规则臂。
即：把 10% 权重换成**随机种子**的 gbm，组合夏普反而比定稿高 0.054。
这不是说基线是假的（安慰剂臂的 A 腿主体仍是 42f，与基线不是同一个对象），
但它证明了一件事：**组合夏普对 A 股腿的小幅扰动有 ±0.03~0.05 的噪声带**。
→ 头条数字必须写成 **1.41 ± 0.05**，不能写 1.4114。

**(2) 滚动窗口胜率 0.1818（11 窗口只赢 2 次）。**
fused 臂在绝大多数子窗口里**打不过基线** → gbm 的增量不是"某些市场环境下有效"，
而是"整体上无效且不稳定"。

### 11.5 结论

**P18 否决 → 换源线（"给 42f 换一个更强的 alpha 源"）彻底封线。**

- 42f 与 gbm 的同日截面相关中位数只有 0.0896（**正交性成立**），
  但正交 ≠ 有增量：gbm 在 42f 之上拿不到任何稳定提升。
- 叠加 placebo 的价值在这里体现得最清楚：**如果只跑规则臂，
  `fuse_w0.10` = 1.3427 / `fuse_w0.20` = 1.3794 这些数看起来都还挺体面，
  很容易被当成"有提升"—— 是安慰剂臂把这件事证伪的。**
- 加上 P17 的结论（类内选标的的上界 ≤ +0.48 且 3/5 窗口 ≤ +0.14）、
  P8（暴露中性化生产口径是负的）、P9（日历对齐零信息）、
  §八 的换源预筛选（8 候选全灭 + DSR 封线）——
  **多资产线的研究部分到此为止，没有剩余的"可探分支"值得再花机时**。

**定稿不变**：`multi_asset_final` = A股腿 42 因子 Top60/ndrop5 **50%** +
ETF 袖套（gold/bond/commodity 各 1/3，类内等权，每月回类间等权）**50%**，
静态划分、腿间不再平衡。
**main 1.4114 / oos 1.0691**（A腿 0.8661，回撤 −7.96%，年化 42.22%）。

### 11.6 OOS 为什么没跑

main 窗口的 (a) 已判否（Δ = −0.032），**在看到 main 结果之后再补跑 OOS
只会制造分叉路径**（可以一直换 seed / 换窗口直到 OOS 好看）。
按 §10.2 的设计，OOS 的作用是"main 通过后的确认"，main 没通过就不必确认。
产物 `multi_asset_p18_oos.json` 因此不存在 —— 这是**按预注册执行**，不是漏跑。
（`multi_asset_p18_oos_smoke.json` 是跑之前的管道冒烟，不参与判定。）

### 11.7 这一轮的通用铁律

> **正交性成立 ≠ 增量成立。**
> 两个信号源截面相关低，只说明"它们看的是不同的东西"，
> 不代表"把它们合起来会更准"。判增量必须配 **placebo 对照**
> （把增量源换成随机种子），且必须用**滚动窗口胜率**看稳定性，
> 只看全窗口的一个夏普数会被噪声骗过去。
>
> **并且：安慰剂赢过规则臂这件事本身就是结论。**
> 当全场最高分是安慰剂时，正确的反应不是"挑那个安慰剂"，
> 而是"承认这个指标的噪声带宽 ≥ 0.05，把头条数字按区间报"。

### 12.3 E2E 抓到的 4 个 bug（都已修）

`scripts/test_multi_asset_line.py` 第一次跑出 **8 项失败**，其中 **4 项是真 bug**：

1. **合并持仓丢了 A 腿**（只剩袖套 9 只）
   - 根因：`run_line` 的返回值里**没有** `positions` 字段（持仓由它自己写进
     holdings 文件），而合并逻辑写的是 `a_res.get("positions")` → 永远是空 dict。
   - 修法：从 A 腿的持仓文件读，并加**一致性断言**（持仓文件与撮合结果
     不一致就拒绝写账本，不写出一份持仓残缺的合并账本）。
2. **整手向下取整让"类间等权"偏了 4.7%**
   - 根因：511020 单价 ~103 元 → 一手 10,300 元，而单只目标权重只有
     55,555（1/9）的 18.5%。单纯向下取整 → 高价标的系统性欠配 →
     实测三类权重偏成 gold 34.8% / bond 30.3% / commodity 34.9%。
   - 修法：改成**两阶段**——先向下取整记零头，再把剩余现金按
     **余数最大优先**补成整手（每只最多补一手）。
3. **净值历史同日重复点**
   - 根因：同一成交日重跑（幂等重试）时直接 `append` → 净值序列出现假的 0% 区间。
   - 修法：`_append_nav()` 同日期**覆盖**而不是追加。
4. **"下次调仓"显示 0 天**
   - 根因：多写了个 `0 if reb`，刚调完仓显示成"今天还要调"。
   - 修法：去掉该分支，公式本身 `(trade_idx-anchor) % 21` 就给 21。

另外 4 项失败是**测试断言过严**（不是产品问题）：
A 腿建仓 58 只（整手约束，见 §12.6）、目标权重合计 0.999999（JSON 存 6 位小数）、
每只权重 0.111111（1/9 存成 6 位小数）、净值点数（bug 3 的连带）。

### 12.6 A 腿的现金闲置：**这是产品化过程中最实的一个发现**

研究端的 A 腿跑的是 **100 万 + 小数股**；产品端的多资产线 A 腿只有
**50 万 + 整手 100 股**。这两条差异叠加出一个研究端**根本不存在**的问题：

`scripts/diag_a_leg_budget.py` 逐只打印了首笔建仓的约束来源：

| 约束 | 影响只数 | 说明 |
|---|---|---|
| 买不了整手 | 1 只 | 预算 7,900 元买不起一手（股价 > 79 元） |
| 流动性门槛拦下 | 1 只 | 920020.BJ 当日成交额 421 万 < 门槛 500 万 |
| 被流动性上限压缩 | 0 只 | — |
| **实际投入** | **430,478 / 500,000 = 86.1%** | **13.9% 的资金躺在现金里** |

根因不是那 2 只，而是**整手取整把零头全扔了**：
`int(budget/p/100)*100` 每只丢掉不足一手的零头，60 只合计丢掉 ~6 万
（≈ A 腿 12%）。**研究端用小数股，永远不会有这个损耗。**

修法（`run_line` 新增 `lot_remainder` 开关，**只对多资产线开启**）：
先按整手向下取整记下零头 → 再把剩余现金按**零头最大优先**补成整手
（每只最多补一手，且不跌破 5% 现金储备线）。

| 指标 | 修之前 | 修之后 |
|---|---|---|
| A 腿持仓数 | 58 | **59**（只剩 1 只被流动性门槛合法拦下） |
| A 腿投入率 | 81.2% | **94.94%**（目标 95%） |
| 袖套三类权重 | gold 34.8 / bond 30.3 / commodity 34.9 | **33.3 / 33.3 / 33.3** |

> ⚠️ 为什么只给多资产线开这个开关：其余 5 条线是**既有纸面账户**，
> 改了它们的整手口径，已展示的历史净值就无法用新代码复现。
> 要不要把其余 5 条线也一起改 → 走「先给方案、等拍板」的流程，不擅自改。

### 12.7 袖套撮合器又抓到 2 个 bug（E2E 第二轮）

1. **现金双扣 → 负现金**
   零头分配阶段把"补一手"的钱从 `cash` 里扣了一遍，执行阶段又扣一遍 →
   袖套现金变成 **−42,911**。修法：分配阶段只算"可分配闲钱"，执行时统一扣。
2. **先买后卖超配 → 首笔 9 买 8 卖 + 零股持仓**
   研究侧 `L3.simulate` 第 4 步是"卖出超配"，但语义是**只削买之前就超配的**
   （买的时候 `cur >= want` 就跳过不买，事后削掉）。产品侧一刀切地卖所有超配：
   - 把整手取整/补手产生的超配又卖回去 → 类间等权重新偏掉；
   - 按 `proceeds/sell_px` 减股数 → 产生**零股**（A 股/ETF 只能整手卖，
     零股必须一次性全卖）→ 持仓变成不可交易状态。
   修法：只削买前超配的，且**按整手卖**（卖不完的零头留着，误差 < 1 手）。

修完袖套口径夏普从 1.6241 → **1.6261**，组合从 1.4115 → **1.4133**，
而与研究实现的**逐点等价性仍是 6.661e-16**（board_lot=0 路径未受影响）。

### 12.8 幂等：同一成交日重跑会重复调仓

袖套的 `reb_anchor_idx` 是在**首次建仓**时设成 `trade_idx` 的，而
`is_rebalance_day(trade_idx, anchor) = (trade_idx-anchor) % 21 == 0`
在 anchor 当天**恒为真** → 同一成交日重跑会再调一次仓（账本 76 → 85 行）。
修法：新增 `last_reb_idx` 记住上次调仓的交易日索引，同日不重复调。

> 这条是**幂等性要求**（同一输入必须得到同一账本），不是优化。

### 12.9 整手约束下「类间等权」是**做不到**的 —— 必须当成优化问题解

上一节把袖套改成整手成交后，出现一个必须讲清楚的事实：

**袖套每只标的的目标 = 净值/9（50 万 → 55,556 元），但 ETF 的「一手金额」差 66 倍：**

| 标的 | 2026-10-19 价 | 一手金额 | 一手 = 单只目标的 |
|---|---|---|---|
| 159981 商品 ETF | 1.810 | **181 元** | 0.3% |
| 518880 黄金 ETF | 8.556 | 856 元 | 1.5% |
| 511010 国债 ETF | 140.987 | **14,100 元** | **25.4%** |
| 511020 国债 ETF | 118.814 | 11,881 元 | 21.4% |

也就是说：**债券类的一手就等于单只目标的 1/4**，「每只 1/9」在债券类
用整手根本凑不出来。逐只向下取整 → 债券类系统性欠配
（实测类权重 gold 34.8 / bond **30.3** / commodity 34.9，偏 3.5 个点）。

**解法（不是"凑"，是显式优化）**：`_plan_sleeve_lots()` 用**局部搜索**求整手解：

- 起点 = 逐只向下取整；
- 反复尝试「某只 ±1 手」的移动，取**三类权重相对 1/3 的最大偏离最小**、
  且**总成本 ≤ 现金**的那一个；
- 目标函数用「类权重偏离」而不是「总额误差」——策略的承诺是**类间等权**，
  总额差 1% 无所谓，类权重偏 1 个点才是违约。

实测（2026-10-19 建仓，50 万）：

| 方案 | gold | bond | commodity | 最大偏离 | 投入率 |
|---|---|---|---|---|---|
| 逐只向下取整 | 34.8% | 30.3% | 34.9% | 3.5 pt | 95.4% |
| 逐只 floor + 贪心补手（按股数排零头） | 34.1% | 32.1% | 33.8% | 1.16 pt | 98.2% |
| **类分组局部搜索** | **32.6%** | **34.0%** | **33.3%** | **0.70 pt** | **99.8%** |

**为什么债券类反而略超配（34.0%）：** 511020 一手 11,881 元，
类目标 166,667 元 → 整数解只能是 5 手（59,405）→ 债券类最少只能到
158,007 元（偏 −5.2%）或 169,892 元（偏 +1.9%）。
现金是硬的：gold+commodity 各自只能凑到 ~166,000，
剩下的空间只够债券类多占 3,225 元。**0.70 个点就是整手粒度下的物理下限**，
不是算法没调好。

> 顺带修掉一个隐蔽 bug：原来的"贪心补手"按**股数**排零头，
> 但 511020 一手 1.2 万、518880 一手 856 元，同样"差 0.6 股"金额差 20 倍 →
> 低价 ETF 抢走补手名额、高价标的继续欠配。补手必须按**金额**排序，
> 且判据是「误差下降量 2×缺口 − 一手金额 > 0」。

### 12.10 类权重偏离：**头条数字是采样口径误导，真正的结论是「月度漂移」**

Parity 回测（产品口径，2023-05 → 2026-05，141 个采样点）报出
「类权重最大偏离 均值 2.85 pt / 最差 7.10 pt」，第一反应是撮合器坏了。

**用产品代码单独跑袖套复核后，这个归因是错的**（`scripts/diag_sleeve_drift.py`，
产物 `data/backtest/diag_sleeve_drift.json`，2020-01 → 2026-10，74 次调仓）：

| 口径 | 均值 | 最大 |
|---|---|---|
| ① **调仓日**偏离（刚调完仓那一刻） | **1.0 pt** | 2.6 pt |
| ② 两次调仓**之间**的最大偏离 | **2.0 pt** | 5.3 pt |
| ③ 全部采样点 | 1.3 pt | 5.3 pt |

逐年调仓日偏离：2020 1.25pt / 2023 0.78pt / 2025 1.07pt / 2026 1.32pt。

**结论：**
1. **调仓日偏离 ≈ 1 pt**（不是 7 pt）→ 撮合器**确实把类间等权做出来了**，
   剩下的 1 pt 是整手粒度的物理下限（§12.9）。
2. Parity 那个 2.85 pt 均值是**按周采样**造成的：袖套每 **21 个交易日**才调一次
   仓，141 个采样点里只有约 1/3 是调仓日，其余是**两次调仓之间的价格漂移**。
   **这是策略设计的固有成本，不是实现 bug。**
3. → 「类间等权」的诚实表述是：**月度再平衡，调仓日达成 ≈1pt 等权，
   区间内最多漂到 ≈5pt**。若承诺是「持续等权」，那必须提调仓频率
   （代价：换手↑ + 整手误差↑），那是**策略变更**，不是修 bug。

**读法（三条，都重要）**
1. **42f 是「大盘 / 低波 / 价值倾向」的组合**，不是「全市场选股」。
   - 跑赢大盘：上证指数 **4/5** 窗口为正（全基准里最高）、沪深300 3/5；

2. **所以"跑赢大盘"这句话必须限定成"跑赢大盘"**：
   上证指数 4/5、沪深300 3/5 成立；换成中证500/创业板指就变成 2/5，
   换成全市场（中证全指）就只剩 2/5、main ≈ 0。**同一个策略，换个"大盘"结论就变。**
3. **这恰好和 §12.14 D 的"降波动"结论自洽**：
   波动更低的组合天然来自大盘价值股（β vs 上证 0.669 最高、vs 创业板 0.229 最低）。
   → 42f 的定位应写成 **「低波动的大盘 A 股组合」**，不是「选股 alpha」「全市场增强」。

**对用户的实盘含义（新增，比之前更具体）**
- 42f 适合的角色：**组合里的 A 股大盘底仓**（低波动、中等收益、与中小盘/成长低相关）。
- 42f **不适合**的角色：全市场代理、成长行情的参与工具。
- 若用户想同时拿到中小盘/成长暴露 → **靠袖套（黄金/债券/商品）与 A 股腿的低相关（ρ 0.238）**，

#### F2. 差点被旧批次覆盖：同一产物的"错序交付"风险（2026-11-01 实查）

- 一个 10-31 11:24 的旧批次（`--phase all`，`multi_asset_p11_alpha_beta.py`）在今天才送达通知，
  **exit code 1、无 traceback、日志最后一行是「✓ 写出」** → 按台账既有判据 = **外部 kill**，
  且它**没有**落在我的 `--phase bench`（11-01 06:50）之后 → 产物没被污染。
- 核查方式（不靠时间线推断）：**指纹清单条目 mtime（06:50:14）== 产物实际 mtime**，
  且 `market_proxies` 三个键齐全、main 分解与中证全指列数值与台账一致。
- ⚠️ **指纹哈希是 `normalized-json-v1`**（排除 `wall_s` 这个墙钟字段），
  所以**不能拿原始字节 sha256 去比** —— 我第一次用 `sha256(open(f,'rb').read())` 去比，
  得到"清单 7cc99ecd vs 当前 7b9984f5"的假不一致，**实际是算法口径不同**。
  → **教训：比对指纹必须走 `artifact_manifest.py verify`，不要自己按字节算 sha。**
- **新增铁律**：同一产物被多个批次（重跑 / 旧批次迟到 / 手动补跑）写过时，
  **必须用清单 verify + 关键字段独立核对**来判定"现在磁盘上是谁写的"，
  **禁止用时间线或记忆推断**；重跑后立刻重建清单，别让清单落后于产物。

#### G. 台账铁律补强（本节的三条教训）

1. **只报 `alpha_sharpe` 不报 `excess_sharpe` = 误导**（同一产物两个口径，必须同时报）。
2. **不同基准不能混在一列**：ETF(510300) 与指数(000300) 是两个东西，
   覆盖率不同、口径不同、结论可相反（main: ETF +0.050 vs 指数 +0.291）。
3. **基准必须覆盖"整个市场"**：只跟沪深300比，会漏掉小盘/微盘段的表现；
   **中证全指才是全 A 股的无偏基准**。任何"我们跑赢了大盘"的表述，
   必须能指出是**哪个大盘**。

### 12.17 文档审计链加固（2026-11-01）：把"P18 文档没人审"变成"2066 条断言 + 逐锚点自证"

#### A. 发现的真实问题

P18 文档（`docs/backtest/P18_FUSE_GBM_2026-11-01.md`）由 `gen_p18_doc.py` 从产物渲染，
数字零手抄 —— **看起来**不需要审计。但审计器里 P18 的断言段被门控成

#### B. 三处修改（都在 `backend/scripts/audit_doc_numbers.py`）

| # | 问题 | 修法 |

| 1 | **门控语义错误**：`and` 把 main 段和 oos 段一起跳过 | 拆成 `P18_MAIN_READY`（main 段）/ `P18_OOS_READY`（oos 段）两个独立门；main 产物在就审 main |
| 2 | **锚点定位用表序号** → 往 P18 文档插一张表，后面所有锚点全位移（§12.13 P4 教训重演） | 改成 `('row', 行标签)` 定位；再叠一层**列名筛选**（同一行标签可能在多张表出现，如 P18 的 '0.10' 同时在 placebo 表和机制表） |
| 3 | **注入器不支持行标签定位** → 负向自检把 P18 全跳过（P18 是盲区） | 注入器补上行标签分支，与 `check()` 同语义 |

原 `--neg` 自检是**每文档注入一处**（上限 100）→ 只能证明"这个文档被抓到"，
**不能证明每一条锚点都真的生效**（写错行列 → 静默不比对 → 绿灯）。
新增**逐锚点穷举**：每条锚点单独注入 → 必须逐条失败。

1. **按文本找单元格会找错列**：P2 表里「样本外」与「较差窗口」两列文本**完全相同**

   → 改为按 **(行索引, 列索引)** 定位。
2. **只注入第 0 个数字会误判**：复合格（`1.3767 (+59.0%)`）的锚点可能盯第 1 个数字
   → 改第 0 个，锚点照样通过 → 被误报成"形同虚设"。
   → 改为**逐个数字位置注入**，任一位置能破坏即算有效。

#### E. 产物清单：区分「故意不产出」与「真丢失」

`multi_asset_p18_oos.json` **按预注册故意不存在**（main 被 (a) 否决 → 不跑 oos）。
原实现把它和"产物本来存在但丢了"混在同一个 `missing` 列表 → 每次 verify 都打同一条
⚠️ 假警报 → **真故障发生时会被淹没**（告警疲劳 = 告警失效）。
新增 `EXPECTED_MISSING`（必须写明"按预注册不产出"的理由与章节号）：
- 假警报与真故障分开记；
- 反向门：标记为「预期缺失」但文件**突然出现** → 报"需重新 build 登记指纹"

#### G. 工程经验（补进台账铁律）

- **"由生成器渲染"不等于"已被审计"**：生成器算错时文档照样自洽。
  审计断言必须**独立于生成器**、直接读产物。
- **门控要按"依赖粒度"拆**：一个 `and` 把两段一起跳过 = 一段永远没人审。
  正确写法：`main 段依赖 main 产物` / `oos 段依赖 oos 产物`。
- **"预期缺失"和"真缺失"必须分表**：混在一起 = 假警报淹没真故障。
- **注入自检要能证明"每条锚点都生效"**：每文档一处不够，要逐锚点穷举。
- **自检自己会骗人**：定位歧义（重复文本 / 多数字复合格）会让自检误报"锚点无效"。
  自检代码的定位必须与被检代码**同语义**。

### 12.18.2 门禁的门自己是坏的：CRLF 行尾

| 项 | 内容 |
|---|---|
| **现象** | `scripts/pre-commit-check.sh` 和 `scripts/quick-check.sh` 是 **CRLF 行尾** → bash 解析到 `for pattern in "${SENSITIVE_FILES[@]}"; do\r` 直接语法错误 → **脚本第一行都没执行**。但文件一直在、一直被文档和 commit hook 引用、看起来"在跑" |
| **证据** | `file scripts/pre-commit-check.sh` → `with CRLF line terminators`；`bash -n` → `syntax error near unexpected token 'do'`。`git show HEAD:scripts/pre-commit-check.sh` 同样坏 → **不是本次改动引入，是历史遗留** |
| **范围** | 全仓 47 个 .sh 里**只有这 2 个**是 CRLF（其余 43 个是 LF）→ 典型的「从 Windows 编辑器/网页复制粘贴引入」，且没有任何检查发现它 |
| **修法** | 两个文件转 LF。转完 `bash -n` 全仓 47 个 .sh **0 语法错误** |
| **新增闸门** | `backend/scripts/check_gates_runnable.py` —— 「门禁的门也要能跑」：所有 `.sh` 必须是 LF + 通过 `bash -n`；8 个关键闸门脚本必须存在且可解析。**这条闸门自己就是防「门禁假存在」的** |

### 12.18.3 门禁依赖的工具本身是坏的：shebang 指向旧用户名

| 项 | 内容 |
|---|---|
| **现象** | `backend/.venv-py313/bin/pyflakes` 的 shebang 写着 `/Users/ronghui/...`（旧用户名）→ 直接执行报 `bad interpreter: .../python3` |
| **绕法** | 一律用 `<venv>/bin/python -m flake8`（绕开 shebang），并显式 `env -u PYTHONPATH -u PYTHONHOME`（见 MEMORY：PYTHONPATH 指向 Hermes venv 会污染 pip/解释器行为） |

### 12.18.4 教训（新增工程经验第 16 条）

> **一个门禁「有文件 / 在 CI 里被引用 / 在文档里写着」不等于「它在跑」。**
> 必须有一条**独立的**检查去验证**门禁本身可执行**（行尾 / 语法 / 依赖工具可用），
> 否则就是「门禁的门没锁」——比没有门禁更危险，因为它提供虚假的安全感。
> 验证门禁有效性的唯一方法是**负向注入**：故意制造一个该门禁该抓的错误，
> 确认它真的报错、且退出码非 0。**只跑通一次不算验证过。**

## 12.20 文档审计链加固（第二轮，2026-11-01 晚）：回填器的三处地雷 + 「只修判不过的格」

### A. 发现的三处地雷（都不在「数字对不对」这一层，而在「谁来改、怎么算对」这一层）

1. **回填器无视锚点第 6 位（idx）** → `--apply` 会把 P12 的 58 个「子窗口众数」格从
   `0.15 (1/4)` 改成 `1.00 (1/4)`（括号里的 `1` 才是锚点盯的数字，第一个 `0.15` 是别的东西）；
   而审计器当时也只查**第 0 个**数字 → **两边一起失灵**，正是 §12.17.G 那条铁律
   （共享实现 = 互为盲区）的第二次应验。
   ⚠️ 这 58 格在两种舍入规则下**逐字符相同** → 不是本次改出来的，**是一直埋着的地雷**。
2. **回填器把 tuple 表定位当表序号** → P13/P15 的 `('row', …)` 锚点直接崩
   （`tidx >= len(blocks)` TypeError）→ 审计器能跑、回填器跑不了。
3. **回填器与审计器的「什么算对」是两套约定** → 回填器想改 42 格，
   而那 42 格**没有一格是真漂移**，全是约定差异：文档用 U+2212 排版减号、
   平局舍入取法与人写文档不同、手写值与重算值差 1ulp。

### B. 修法（唯一真源放在审计器）

| 修法 | 说明 |
|---|---|
| `fmt_like(old, want, idx)` | 支持「复合格里第 N 个数字」；实现**下沉到审计器**，回填器只代理 |
| 回填器表定位 | 改走 **AUD.resolve_table_idx**（与审计器同一份实现），不再各写一套 |
| **回填器只修「审计器判不过」的格** | 判据直接用 `AUD.target_number(old, want, idx)` → 「什么算对」有了**单一判定函数** |
| `_fmt_dec` | 用 `ROUND_HALF_UP`（f-string 平局取偶会把 31.45 写成 31.4，与人写文档相反）+ `format(d,'f')`（避免 `0E-10`） |
| `fmt_like` 保留减号字形 | 原格是 U+2212 → 新值也用 U+2212；原格是 ASCII `-` → 保持 ASCII |

> 「只修判不过的格」这条是关键：回填器**不是**「把我的规范格式全刷一遍」，
> 而是「把错的改对」。判据交给审计器那个函数后，两边不可能再分叉 ——
> 修之前 42 格差异**全是约定差异、没有一格是真漂移**，如果照旧刷一遍，
> 就是把 42 个正确的格子改坏（而且改完审计器还判它们对）。

### C. 验收（2026-11-01 晚）

- 表格语义断言 **2237** 条 + 文本格 9 条 + 判据符号 20 条 + 正文数字 49 条 → **全过**
- 产物指纹 **58 个**与清单一致（`multi_asset_p18_oos.json` 按预注册属「预期缺失」）
- 负向注入：**2237 / 2237 锚点逐条可被破坏并抓到，漏抓 0**
- 回填器 dry-run：**改动 0 格、未定位 0 个锚点**（修复前：崩溃 + 42 格待改）

### D. 工程经验（补进台账铁律）

- **「共享实现」必须再加一条交叉约束**：审计器与回填器共用判定后，
  仍要有「回填器只修审计器判不过的格」这条不对称约束 —— 单靠"共用"会把
  两边的**同一个错误**放大成"两处都对"。
- **回填器的正确形态是「修复器」不是「格式化器」**：前者只在审计器报错时动手，
  后者会把「约定差异」当成「错误」批量改写文档。

> 来源：一条迟到的后台通知（第九次重播）里露出破绽——当日产物清单里
> `multi_asset_p18_oos_smoke.json` 明明**被台账正文引用**，却不在指纹清单里。
> 于是去查"到底有多少文档引用件没被保护"，查出一个洞。

### A. 洞有多大

| 口径 | 数量 |
|---|---|
| `data/backtest/` 磁盘上的 json | **178** |
| 指纹清单保护 | **58**（当时） |
| 文档正文点名的产物 | **54** |
| **文档点名但清单不管（差集）** | **21** |

这 21 个里有 `pool_partition.json` / `turnover_truth.json` / `fundamental_ic.json` /
`gbm_lag1.json` / `methods_*` / `multi_asset_leg*.json` 等
—— 全是 A 股腿与基线修正那批的证据件，被 `CONCLUSION_2026-10-27`、
`POOL_PARTITION_2026-10-30`、`METHODS_RESEARCH_2026-10-26` 等文档正文指着。

### B. 篡改实验（决定性证据）

改 `pool_partition.json` 的 `baseline_sharpe`（0.86609 → 0.9545）与
`universe_size`（5513 → 5614），然后跑两个门：

| 门 | 结果 | 为什么 |
|---|---|---|
| 指纹门 | ✅ 通过 | 这个文件根本不在清单里 |
| 文档数字审计 | ✅ 通过 | 审计只校验**文档里写的那几个数**，不校验整文件 |

→ **两个门同时放行**。文档引用的产物，只要改的不是被点名的那几个数，
就能被静默改掉，而所有门都是绿的。这正是本项目从头到尾在防的那类事故。

### C. 封堵（三处改动，全部在 `backend/scripts/artifact_manifest.py`）

1. **21 个文档引用件全部纳入 TRACKED**（清单 58 → **79**）
2. **易变白名单补齐**：`wall_s` → `wall_s / total_wall_s /
   mainloop_sub_progress_update_s / precompute_sub_build_date_index_s / generated_at`
   （扩了白名单就必须**升指纹算法版本** `normalized-json-v1` → **`-v2`**，
   否则旧清单算出的哈希会被误读成"产物被覆盖"；
   `candidate_main_best_rule_arm` 等**确定性选择元信息不剥**——剥了就等于放弃对
   "选中了哪条规则"的保护）
3. **新增「文档引用 ⇒ 必须入清单」闸门**（自维护）：
   `doc_cited_artifacts()` 现场扫 `docs/backtest/*.md` 正文里点名的产物，
   减去 TRACKED，非空即 verify 失败（清单自报 + 当场重算**两个口径都查**）。
   → 以后新文档引用新产物、而没登记进指纹清单，**当场报错**，不再靠人记得。

### D. 复测（同一篡改，改完再改回来）

```
篡改 pool_partition.json → ❌ 产物指纹校验失败（1 项）：
   - pool_partition.json: sha256 不符
      清单 7245eb2d2edc7d0b… / 当前 c5c2b1c5902f5966…
按字节还原 → ✅ 79 个产物与清单一致
```

**洞已堵死并有实证**。文档数字审计同步复跑 RC=0（2237 断言），
`uncovered_audited = []`、`uncovered_doc_cited = []`。

### D2. 闸门的第一道自检：**它先把我自己拦下来了**

加完闸门、写完本节正文、准备提交时，提交前的 verify 突然变红：

```
❌ 产物指纹校验失败（1 项）：
   - verify_10y_pit.json: 文档新引用了未登记产物 → 需登记进 TRACKED 并重新 build
```

原因很讽刺：我在本节 A 段**举例时点了 `verify_10y_pit.json` 的名字**
（它原本既不在 TRACKED、也不被任何文档引用 → 谁也不管它）。
一句举例 → 它变成"文档引用件" → 新闸门当场发现没人保护它 → **verify 变红**。

处置：把它登记进 TRACKED（它的易变字段只有 `wall_s`/`total_wall_s`，白名单已覆盖），
清单 79 → **80**，闸门转绿。

> 这比任何设计论证都有说服力：**差集藏不住，而且当场就藏不住**。
> 如果这条闸门是"以后靠人记得补"，今天这份文档就会带着一个红灯提交出去。

### E. 教训（写给以后的我）

- **"我建的门" ≠ "我以为的门"**。指纹门覆盖 58/178，看着像全覆盖，
  其实是白名单；白名单是我手写的，所以**没被引用的证据件永远进不来**。
- 守卫网必须**从被守护对象反向推导**（文档引用了谁 → 谁就得被保护），
  而不是从守卫对象正向枚举（我记得谁 → 谁被保护）。
  本次把 `doc_cited_artifacts()` 做成清单的**自动输入**，差集就再也藏不住。
- 篡改实验要**还原**（本节 D 已按字节还原，`git diff` 干净）。查洞可以，
  留一个被改过的证据件，比洞本身更糟。

## 12.24 指纹门第二轮扩面：连"故意不保护"的都要显式登记（2026-11-01 21:10）

> 触发：把 §12.23 的闸门扫全整个 `data/` 树（实测只有 322 个 json，扫全树很便宜）
> → 发现**还有 26 个被文档点名、却没人守护的证据件**，主要在 `data/strategy_baseline/`
> （旧文档 BASELINE_CORRECTION / CONCLUSION / METHODS_RESEARCH 引用的
> A 股腿基线、IC、DSR、随机对照产物）。

### A. 关键设计：**不保护的东西也要写进清单**

| 类别 | 处置 | 数量 |
|---|---|---|
| 跨目录证据件（`data/strategy_baseline/` 23 + 静态定义件 3） | **纳入指纹**（`TRACKED_EXTRA`，键 = 相对 ROOT 的路径） | 26 |
| 活状态（`data/paper/` 3、`data/signals/` 3、`data/tdx_daily/` 1） | **显式豁免**，并写进清单的 `live_state_excluded` | 5 |

- 活状态**不能**做指纹化：每周一重写 / 每天重写 → 指纹门会天天红 → 告警疲劳。
  它们的可复现性由各自管道的**幂等性**保证（同成交日重跑不重复下单），
  不是靠哈希锁。**但排除必须是显式的**：否则下一个人会以为它们被保护着。
- 扫描范围用**全树**而不是目录白名单：`data/` 全树只有 322 个 json，扫全树很便宜；
  列白名单会重犯"没被列到的就没人管"的原罪（这正是 §12.23 的教训）。
- 键空间：`data/backtest/` **直属**文件用 basename，其余用相对 ROOT 的路径
  （避免同名文件跨目录撞键；键里带 `/` 的一定是路径）。

### B. 篡改实验（跨目录件）

```
篡改 data/strategy_baseline/risk_parity_dsr_final.json
  → ❌ 产物指纹校验失败：data/strategy_baseline/risk_parity_dsr_final.json: sha256 不符
按字节还原 → ✅ 110 个产物与清单一致
```

### C. 现状

- 指纹产物 **110** 个（`data/backtest` 直属 84 + 跨目录 26）
- 文档点名 **90** 个 → 未覆盖 **0**；活状态豁免 5 个（显式登记）
- 文档数字审计 RC=0

### D. 教训（补 §12.23 的 E）

白名单式覆盖**永远差一口**：58 → 84 → 110，三轮扩面，每一轮都是"又发现一个漏网的目录"。
所以正确做法不是"把名单补全"，而是让**被引用对象自动成为清单输入**（已做：
`doc_cited_artifacts()` 现场扫文档），并且把**故意不保护的**也写进清单
（`live_state_excluded`）——**连例外都要显式登记**，否则例外会变成盲区，
而盲区看起来和"已保护"一模一样。

## 12.25 bash 的 locale 陷阱：`$VAR` 后面紧跟中文 = 变量名被吞（2026-11-01 23:2x）

> 触发：一条**迟到的手工运行回执**（今天 12:29 与 12:59 两次）报
> `scripts/weekly_paper_portfolio.sh: line 67: RC: unbound variable`。
> 排期跑（launchd）一直正常 → 说明**触发条件与环境有关**，不是逻辑错。

### A. 根因

bash 在 **UTF-8 locale** 下把紧跟变量名的**非 ASCII 字符算进变量名**：

```bash
echo "失败 RC=$RC，日志：$LOG"     # UTF-8 locale
# → bash: RC，: unbound variable   （变量名其实是 "RC，"）
```

- `LC_ALL=C`（launchd 的环境）→ 正常；`en_US.UTF-8`（终端）→ 必炸。
- 报错行号指向第 67 行，但**赋值在第 51 行** → 差 16 行，正是"变量名被改名"的特征
  （bash 报的是"引用未定义变量"的那一行，不是"赋值"的那一行）。

### B. 为什么危险（不只是日志难看）

| 位置 | 触发条件 | 后果 |
|---|---|---|
| line 67 `RC=$RC，` | 纸面盘返回非 0 | 工作**已完成**，但状态行与**真实退出码**丢失（变成 1） |
| line 46 `$ETFRC）` | **ETF 刷新失败** | 脚本在**跑纸面盘之前**当场退出 → **整条周线被跳过**，且报错语焉不详 |

line 46 那条才是真雷：TDX/网络抖一下 → 周一 17:40 的排期跑直接死在第一步，
用户看到的是"脚本崩了"而不是"ETF 没刷到"。这正是"周一静默失败"那一类风险。

### C. 修复与验证

- 全部改成 `${RC}` / `${ETFRC}`（花括号显式截断变量名），并在脚本头写死规矩：
  **变量后面紧跟中文/全角标点，一律写 `${VAR}`**。
- 全仓扫描（Python 逐字节扫所有 `.sh`）：`$VAR` + 非 ASCII 的隐患点**只有这 2 处**，
  都在同一个脚本（其它脚本的中文提示语里变量后面都是空格或 ASCII 标点，安全）。
- **桩化实跑验证**（临时 ROOT + 假 python，UTF-8 locale，三条路径）：
  | 路径 | 期望 | 实测 |
  |---|---|---|
  | 纸面盘 RC=3 | 打印 ❌ 行 + 退出码 **3** | ✅ 退出码 3，无 unbound |
  | ETF 刷新失败 | 打印 ⚠️ 行 + **继续**跑纸面盘 | ✅ 继续跑，退出码 0 |
  | 全部成功 | ✅ 行 + 退出码 0 | ✅ |

### D. 教训

- **同一个脚本在 launchd 下正常、在终端下炸** → 先怀疑环境差异（locale / PATH / 工作目录），
  别急着改逻辑。回执里的错误信息含 `�`（宽字符被截断）本身就是 locale 线索。
- bash 的变量名是"字节 + 宽字符"规则，不是纯 ASCII 规则；**中文提示语里带变量是陷阱**。
- 退出码纪律（脚本头注释里那条：`python ... | grep` 会让 `$?` 变成 grep 的退出码）
  只有当脚本能**跑到底**才有意义：崩在第 67 行时，再严谨的 RC 采集也传不出去 ——
  **"记录失败"和"失败被吞掉"是两件事**，先保证路径可达。

## 12.26 回测适配器口径统一：单一权威来源（产品侧，2026-11-01 23:4x）

> 触发：全量单测体检暴露 `tests/unit/backtest/test_backtest_data_adapter_properties.py`
> 红（`test_monthly_returns_analysis_consistency`）+ `tests/unit/infrastructure/
> test_infrastructure.py` 红（`test_middleware_configured`）。**两条都不是回归**
> （今天的提交没碰这两个文件），是契约漂移。

### A. 三处同源缺陷（根因，不是"测试过时"）

引擎的 `portfolio_history` 快照是**每个交易日收盘后**记录的 → 第一个快照 = 第一个交易日
收盘，**不是 t0 初始状态**。适配器（`app/services/backtest/utils/backtest_data_adapter.py`）
有三处把这个当成了 t0：

| # | 位置 | 症状 |
|---|---|---|
| 1 | `_analyze_monthly_returns`：`monthly_values.pct_change().dropna()` | **整月被丢**（首月无返回）→ 热力图少一月；且「月度序列复利」≠「累计收益」 |
| 2 | 同上：`initial_value = df["portfolio_value"].iloc[0]` | 累计收益基准 = 首日收盘 → **首日盈亏整段被排除** |
| 3 | `_calculate_extended_risk_metrics`：`returns = pct_change().dropna()` | 缺 t0→首日这一段 → 期间数少 1（年化指数 252/(N−1)）且首日盈亏不进波动率 / VaR |

外加第 4 处（**口径分裂**）：适配器用 `(年化 − rf) / 年化波动` 重算夏普，引擎用
`日均 / 日σ × √252` → **同一份 API 响应里两个夏普**。

### B. 量化（真实引擎产物 + 构造对照）

| 现象 | 修前 | 修后 |
|---|---|---|
| 夏普（引擎 vs 适配器，同一响应） | 9.340288 vs 12.873346（**差 3.53**） | 完全相等 |
| 月度序列条数 vs 跨的日历月数（真实引擎 case：130 个日度快照） | 5 vs 6（**少 1 个月**） | 6 vs 6 |
| 月度序列复利 vs 末月累计（3 个月 +10%/+5%/−2% 构造） | +2.90% vs +13.19%（**缺口 10.29pp**） | +13.19% == +13.19% |
| 末月累计 vs 引擎 total_return | 相等 | 相等（基准统一到 t0 后仍相等） |
| 年化指数 252/N vs 252/(N−1)（N=1212） | +0.0037pp | 修正（可忽略，但方向对） |

### C. 修法（单一口径来源）

1. **引擎权威值透传**：`annualized_return / volatility / sharpe_ratio / max_drawdown`
   一律优先用引擎返回值（`task_result` 里本来就带着），适配器**不再重算第二套**；
   引擎缺失时才本地兜底。新增 `_prefer_engine()`。
2. **补首段**：收益序列补上「t0 → 首个快照」这一段（期间数恢复 N）。
3. **月度不丢首月 + 基准改 t0**：月度序列覆盖每一个日历月，月度复利 == 累计收益 == 引擎 total_return。
4. `df.sort_index()`：原来 `iloc[0]` 隐含假设历史按时间有序。

**未改的**：引擎侧 `monthly_returns_detail`（`backtest_report_builder` / `backtest_executor`）
仍是"丢首月"的老口径 —— 它被 15 个 strict baseline 金标准（`monthly_returns_detail_length: 61`
+ sha256）锁住，改它要重生成并人工审 15 个策略的首月值 → **单独立项，不夹带**。
适配器与引擎不经过同一条管线（适配器只在 `task_executors` 异步任务链路里调用，
金标准 runner 不调它）→ 本次修复**不动任何已发布基线**。

### D. 测试迁移（不是加兼容层）

- `test_monthly_returns_analysis_consistency`：容差 `0.05` → `1e-9`（原来那 0.05 的宽容
  是在**掩盖基准错**），并新增两条回归：① 月度条数必须 == 覆盖的日历月数；
  ② 月度序列复利必须 == 末月累计收益（正是那个 10.29pp 缺口）。
- `test_extended_risk_metrics_calculation_accuracy`：改成**兜底路径**用例（移除样例里的
  占位引擎指标），保证本地计算本身仍被验证。
- 新增 `test_engine_metrics_passed_through`：锁定"引擎值原样透传"这个新契约，
  并验证派生指标（Calmar）用的是**引擎的年化**而不是适配器自算的 252 交易日年化。
- `test_middleware_configured`：限流中间件当前实现是 `IdentityRateLimitMiddleware`
  （按用户身份计数，`app/main.py:43`），是 `RateLimitMiddleware` 的**子类**；
  旧断言用 `in` 做精确类身份匹配 → 改成 `issubclass` 判定。

### E. 教训

- **同一份响应里出现两个同名指标**，用户无从判断哪个对 —— 这类"双口径"比"算错"更难查，
  因为两个数都"看着合理"（9.34 vs 12.87 都是合理夏普）。发现它靠的是**把两个来源并排打印**。
- 适配器**重算引擎已经算过的指标**是双口径的温床：重算的理由通常是"接口要一份完整的"，
  代价却是两套定义。正确姿势：**透传 + 只补算引擎没有的**。
- 测试失败先分清"**旧契约**"和"**当前实现回归**"：今天的提交没碰那两个文件 → 基线红 →
  迁测试（改断言到当前契约），而不是给生产代码补兼容层。
- 构造对照（3 个月 +10%/+5%/−2%）比随机数据更能把口径缺陷逼出来：真实引擎那个 case
  首月收益恰好为 0，缺口被掩盖，**换成首月有收益的输入才看见 10.29pp 的矛盾**。

| 副本一致 | **110** |
| 缺失 / 不符 | 0 / 0 |
| 哈希模式 | `normalized-json-v2`（**与生成器共用实现**） |

**第一版校验脚本错了 106 个**：最初用**原始字节 sha256** 校验副本 → 110 个里 106 个"不符"。
真相：清单指纹算法是 `normalized-json-v2`（剔 `wall_s` / `total_wall_s` /
`mainloop_sub_progress_update_s` / `precompute_sub_build_date_index_s` / `generated_at`
等易变字段 → 规范化 JSON → sha256），原始字节哈希与它**必然不等**。修法不是手抄一份算法，
而是**直接 `import artifact_manifest.sha256`** → 两端共用实现，算法永不漂移。

### D. 残余风险（诚实披露）

- 现在是 **2 副本**（内置盘 + 1 块外接 SSD），**不满足 3-2-1**：两块盘在同一张桌上 →
  火灾 / 盗窃 / 雷击一次全灭。
- Time Machine 仍处失效状态（目标卷挂不上，与本项目无关）→ 建议单独修。
- 证据核心其实只有 **~2.1 GB**（110 个指纹产物 + 清单 + 台账）→ 上第三副本（NAS / 对象存储）
  成本极低。**待用户决定，不擅自外传数据。**

### E. 教训

- **指纹清单只防"被改"，不防"没了"** → 任何哈希清单都该配一份**存在性副本**，
  否则它只是"曾经存在过的收据"。
- **gitignore 是默认不可见的决策**：一行 `/data/` 让 2 GB 证据集体退出版本控制，
  而没有一个人（大概也包括我）复核过它的后果。给指纹清单做完整性检查时，
  必须同时检查"文件是否在版本控制里 / 是否有异地副本"。
- **备份脚本必须自带校验 + 失败即非零退出**，否则"备份成功"只是一行日志。
- **"106 个不符"的第一反应应是怀疑自己**：指纹算法是清单定义的一部分，
  复制一份算法 = 复制一份会漂移的 bug；正确解是 import 同一实现。

## 12.28 性质测试的"假绿"与"空覆盖"：断言被 except 吞成 skip + CI-only 兜底模型（2026-11-02）

### A. 发现（来自一条迟到的全量单测回执里的 `SKIPPED [1]`）

回执本身大部分是旧信息（两条 FAILED 已被 §12.26 的 `bf12dca0` 修掉），但那条
`SKIPPED [1] 置信区间测试跳过: 模型加载失败: 模型信息不存在: test_model` 挖出两个缺陷：

| # | 缺陷 | 位置 | 后果 |
|---|---|---|---|
| 1 | **断言被 `except Exception` 吞成 skip** | `tests/unit/prediction/test_prediction_engine_properties.py` 4 处 + `tests/unit/models/test_qlib_optimizations.py` 1 处 | try 包住了断言 → `AssertionError` 被当成"环境问题"跳过 → **性质被违反时套件仍报绿（假绿）** |
| 2 | **性质从未被执行（空覆盖）** | 同上 | 引擎的兜底模型只在 `GITHUB_ACTIONS=true` 时启用（`prediction_engine.py:118-123`）→ 本地 `model_id="test_model"` 必抛"模型信息不存在" → 4 个性质测试在本地**永远跳过** |

**缺陷 1 的机理**：`pytest.skip()` 抛的是 `Skipped`（`BaseException` 子类）→ 逃得出
`except Exception`；但 **`AssertionError` 是 `Exception`** → 会被吞成 skip。于是
`assert lower <= predicted_price <= upper` 这类**性质断言失败**的表现是"跳过"而不是"失败"，
套件照样绿。

**缺陷 2 的机理**：fixture 只造了样本数据、没造模型；模型又只在 CI 环境变量下才有兜底 →
"本地绿"与"CI 绿"覆盖的是**不同的代码路径** → 本地的性质测试一直在空跑。

### B. 修法

1. **try 只包"可能因环境失败的调用"，断言一律移到 try 之外**（5 处）；加
   `assert x is not None` 哨兵消掉 Pyright 的 `possibly unbound`。
2. **fixture 复用引擎自己的兜底模型**：`model_loader._create_fallback_model("test_model")`
   → 它把模型与带 `feature_columns` 的 metadata 写进 loader 缓存 → 本地与 CI 走**同一条**
   预测路径。引擎对缺失特征列会用 0 填充并按训练顺序对齐（`_execute_prediction`）→
   兜底模型可直接用，无需训练。
3. `config.confidence_levels` 显式收窄（`levels is not None`），类型检查与运行期同时成立。

|---|---|---|

### D. 顺带查清：`-q` 叠加吃掉汇总行（**不是仓库的锅**）

现象：多次全量运行里 pytest 最终计数行（"N passed in Xs"）消失，只剩 RC=0 与全点进度行。
二分过程：仓库 `pyproject.toml` 的 `addopts` 里**已经含 `-q`**，我再在命令行加一个 `-q`
→ 变成 `-qq`（双静默）→ pytest 不打印最终计数行。用最小 ini 逐项复现 → 定位到 `-q` 叠加。

影响：**仅影响人类可读的计数行**，不影响退出码与失败上报（故意失败的探针证明：RC=1 + `FAILED` 正常）。

hypothesis 插件每次告警。无害，但值得知道。）

### E. 教训

- **"跳过"不等于"通过"**：一条 skip 能把整个性质测试藏起来（空覆盖）；断言被
  `except` 吞成 skip 则是更隐蔽的假绿。skip 是合法的第三种状态，但**只能覆盖环境性失败**。
- 守卫网要同时检查两件事：**断言是否真的被执行过**，以及**失败是否真的变红**。
- 判据：`except Exception` 里只允许包"调用"，**不允许包"断言"**（`AssertionError` 是 `Exception` → 会被吞）。
- 环境开关（`GITHUB_ACTIONS`）会让本地与 CI 覆盖不同代码路径 → 性质测试必须**两端都能跑**，
  否则本地永远在空跑，而"本地全绿"是假象。

## 12.29 回测结果里混进 NaN → 响应是**非法 JSON**（前端整页挂掉，2026-11-02）

### A. 发现（来自一条旧回执里夹带的 `FutureWarning`）

`Series.idxmin with all-NA values ... is deprecated. In a future version this will raise ValueError`
（`backtest_data_adapter.py:479`）→ 顺着这条告警查下去，发现的是**当下就存在的真缺陷**：

| 环节 | 修前 |
|---|---|
| `portfolio_history` 里混进一个 NaN（某天组合估值缺失） | 回撤序列该点为 NaN → `drawdown_curve` 里出现 `{"drawdown": NaN}` |
| `json.dumps` | Python 默认 `allow_nan=True` → 吐出**裸的 `NaN` 字面量** |
| 那是不是合法 JSON | **不是**。浏览器 `JSON.parse` 直接抛 → **整个响应页挂掉**（不是某个字段降级） |
| 若整段历史全为 NaN | 未来 pandas `idxmin` 抛 `ValueError` → 被本函数 `except Exception` 吞掉 → **整个回撤分析直接丢失**；且 `max_dd_idx` 是 `NaT` → 日期字段变成字符串 `"NaT"`（不是合法日期） |

复现（探针，非推测）：`portfolio_history` 第 3 天 `portfolio_value=NaN` →
`json.dumps(payload)` 产出 `..."drawdown": NaN...` → `allow_nan=False` 直接 `ValueError`。

### B. 修法（源头 + 边界两层）

1. **源头**（`backtest_data_adapter._analyze_drawdowns`）：
   - 回撤序列全 NaN / 为空 → 显式返回**零回撤分析**（`max_drawdown=0.0`、日期/起止为 `None`），
     不让 NaN 外泄，也避开未来 pandas 的 `ValueError`；
   - 曲线里缺失的点写 `None`（JSON `null`）而不是 NaN。
2. **边界**（`analysis_models.sanitize_non_finite` + `EnhancedBacktestResult.to_dict()`）：
   递归把**非有限浮点**（NaN / ±inf）换成 `None`。`to_dict()` 正是最终 JSON 的来源
   （调用方 `data=enhanced_result.to_dict()`），这一层兜住**当下与将来**所有泄漏口。
   只在响应边界做，**不改中间计算口径** —— 数值本身仍是 NaN，只是不再以非法 JSON 出网。
   整数保持 `int`（不变成 `3.0`），`bool` 不被当成数值。

### C. 验证

| 项 | 修前 | 修后 |
|---|---|---|
| 探针：含 NaN 的历史 → `json.dumps(payload)` | 含裸 `NaN`（**非法 JSON**） | **合法**（该点为 `null`） |
| 探针：整段全 NaN | `NaN` / 日期 `"NaT"` / 未来 pandas 抛错 | `max_drawdown=0.0`、日期 `None`、曲线全 `null` |
| 新增回归用例 | — | 2 条（`allow_nan=False` 严格断言） |
| 适配器测试文件 | 7 passed | **9 passed** |
| 常数净值（σ=0）路径 | 已安全（0/0 被兜住，不出 inf） | 不变（未动） |

### D. 教训

- **非法 JSON 比数值错更致命**：NaN 让整页响应挂掉，而它只是某一个交易日缺了个估值。
  边界层必须有一条"**输出必须是合法 JSON**"的硬约束（`allow_nan=False` 就能当断言用）。
- `except Exception` 兜住一切，会把**未来版本的行为变更**（pandas 改成抛错）降级成
  "功能静默消失"——所以未来告警要当**红线**查，不是噪音。
- 修法要分层：**源头**（不该产生 NaN）+ **边界**（万一还有别的口子）。只在源头修，
  下次换个路径又会漏；只在边界修，内部口径仍是脏的。

### C. 新发现：`except Exception` 仍会吞掉 AssertionError（§12.28 修法的残留）

§12.28 把"断言移出 try"做到了位，但保留的仍是 `except Exception as e: pytest.skip(...)`：

```python
try:
    result = self.prediction_engine.predict_single_stock(...)   # ← 调用在 try 内
except Exception as e:
    pytest.skip(f"置信区间测试跳过: {e}")
```

try 里只有"调用"，看似安全；但**被测代码内部自己抛的 `AssertionError` 也会落进这个 except**
→ 生产代码里的断言失效被降级成"跳过" → **套件照样绿**。这不是 §12.28 的原病灶（那是"断言写在 try 里"），
但属于同一族：**skip 只该覆盖环境性失败，不该覆盖被测行为违规**。

同类还有两处 `except Exception` 里的"错误信息断言"（`特征提取失败` / `缺失` / `数据` 字样判定），
它们会捕获 try 体内的 AssertionError，再用错误文案做二次判断 → 若断言文案里含"数据/缺失"字样，
**真失败会被误判成"预期的错误信息"而放行**。

### D. 修法

7 处（`test_prediction_engine_properties.py` 6 处 + `test_qlib_optimizations.py` 1 处）
统一加一道**先于** `except Exception` 的守卫：

```python
except AssertionError:
    # 断言失败属于**被测行为违规**，不是环境问题 —— 必须让它红，不能当 skip 吞掉。
    raise
except Exception as e:
    pytest.skip(...)
```

`AssertionError` 是 `Exception` 的子类 → 必须**排在前面**才有效（`raise` 是裸重抛，保持原栈）。

## 12.30 研究产物备份：从"一次性拷贝"到"有排期 + 自毁护栏 + 并发互斥"（2026-11-02）

### A. 触发

一条迟到的备份回执（`proc_8fdfe776154e`）到达：副本 rsync 完成（32 GB），但校验报
`清单产物: 110 | 一致: 1 | 缺失: 3 | 不符: 106`。**时间线核对**：副本目录 mtime
`11-02 00:52`，而修法（`import artifact_manifest.sha256`，与清单共用实现）落在
`295a4f9b`（`11-02 01:38`）→ 这条回执是**修复前**的状态（§12.27 记的"原始字节
sha256 vs normalized-json-v2"那个坑）。当前实测：`110 一致 / 缺失 0 / 不符 0`、RC=0 ✓。

但顺着这条线查下去，发现的是**四个当前仍在的问题**，比那条回执本身重要。

### B. 问题 1：备份**没有排期** —— 副本只在我"记得跑"时更新

`launchctl list` / `crontab -l` 均无备份任务；脚本存在但只能手工触发。
后果：§12.27 建起来的第二副本，**平时并不存在**——它只是一次性拷贝。

### C. 问题 2：openrsync 的 `--max-delete` **不报错、退出码仍是 0**（假成功）

macOS 自带 rsync 实为 **openrsync**（`openrsync: protocol version 29`,
`rsync version 2.6.9 compatible`）。`rsync --help` 里**有** `--max-delete`，但语义与
rsync 3.x 不同：

| 场景（临时目录实测） | 输出 | 退出码 | 结果 |
|---|---|---|---|
| 待删 100 个 + `--max-delete=3` | `Deletions stopped due to --max-delete limit (97 skipped)` | **0** | 删了 3 个、**跳过 97 个** |
| 待删 100 个 + `--max-delete=200` | 无 | 0 | 全删 |

→ **只加 `--max-delete` 等于制造"静默截断删除 + 报成功"的假成功**：脚本会打印
"✅ 备份完成并通过指纹校验"，而副本其实只同步了一部分（若被跳过删除的正好不是
清单里的 110 个产物，指纹校验根本发现不了）。

**修法**（两层）：
1. `--max-delete=50` 限制破坏面；
2. 捕获 rsync 输出里的 `max-delete limit` 信号 → 命中即**备份失败**（`exit 4`），
   **且无论如何都照常跑指纹校验**（不跳过校验——跳过校验等于让失败无证可查）。

### D. 问题 3：`rsync --delete` 的自毁风险（副本会跟着源树一起蒸发)

`--delete` 让副本与源一致，但方向是**双向的**：如果源树被误清空 / 误移动 / 误 checkout，
**唯一副本会跟着一起没**——而这个副本存在的全部意义就是防单点。护栏即上条的
`--max-delete` + 命中即失败（**宁可备份失败并报错，也不能安静地删掉副本**）。

### E. 问题 4：两个排期器会并发写同一副本

落地后有两条排期（Hermes cron 21:30 主 + launchd 22:30 兜底）→ 两个 rsync 同时写
`/Volumes/DATA/stock-platform-backup` 会打架。用 **mkdir 原子锁**（`runtime/backup.lock`）：

| 规则 | 原因 |
|---|---|
| 拿不到锁 → **跳过**（exit 0），不排队 | 避免积压的备份风暴 |
| 残留锁（`started_at` 超过 6h）→ 清理后重试一次 | 进程被强杀不留残留 |
| `started_at` 读不出来 → **不**判定残留 | 宁可多跳过一次，也不能误删活锁 |
| `--verify` **不拿锁** | 备份正在跑时校验仍要如实报告；否则"跳过"会冒充"校验通过" |
| `trap ... EXIT` 释放锁 | 正常退出/中断都清 |

### F. 验证

| 项 | 结果 |

| T2 持有活锁时再跑 | rc=0 + 「已有备份实例在运行 → 本次跳过」→ 不并发写 |
| T3 持有活锁时 `--verify` | 仍如实校验并报 **110/110**（不被"跳过"冒充成功） |
| T4 残留锁（8h 前） | 「清理了残留锁（>6h）→ 继续」→ rc=0 |
| cron 入口 `research_backup.sh` | rc=0，状态文件写入 `state=ok rc=0 \| 清单产物: 110 \| 一致: 110 ...` |
| monitor 探针确定性 | 连续两次输出**逐字节相同**（无时间戳）→ 状态不变时不唤醒 agent |

## 12.31 `norecursedirs=["scripts"]` → `tests/unit/scripts/` **整目录从未被采集**（2026-11-02）

### A. 触发

落地纸面盘观测口径层时顺手查 pytest 采集范围，发现 `backend/tests/unit/scripts/`
里的测试**从来没有跑过** —— 而且其中一条断言已经烂掉。

### B. 根因

`backend/pyproject.toml` 里：

```toml
norecursedirs = ["scripts", "__pycache__", ".git", ".venv", "venv", "dist", "build"]
```

pytest 的 `norecursedirs` 按**目录 basename** 匹配（不是按路径）→ 根目录下**任何**叫
`scripts` 的目录都被排除 → `backend/tests/unit/scripts/` 连同它的 3 条测试一起
从采集里消失了。而且 pytest **不会**报告"某目录没被采集"，所以这个洞是**静默**的。

### C. 烂掉的断言（已被证实会红）

`tests/unit/scripts/test_seed_strategy_configs.py` 硬编码：

```python
assert first == {"created": 6, ..., "total": 6}      # 脚本的 presets 早就涨到 17
```

把 HEAD 版本捞回来单跑（临时文件，已删）：

```
FAILED tests/unit/scripts/test_tmp_oldseed.py::test_seed_strategy_configs_is_idempotent
{'created': 17} != {'created': 6}
1 failed, 2 passed
```

→ 这条测试**如果当初被采集到**，第一次跑就是红的。

### D. 修法

1. `norecursedirs` 去掉 `"scripts"`。
   **不需要它**：仓库根的 `backend/scripts/` 本来就被 `testpaths = ["tests"]` 排除，
   去掉后只有 `tests/unit/scripts/` 恢复采集 → 采集面**只增不减**。
2. 断言改成按 `len(module.DEFAULT_STRATEGY_CONFIG_PRESETS)` 取条数，不写死魔数。
   真正的不变量是**幂等**（第一次全建、第二次全不改），不是"恰好 6 条"。

### E. 验证

- `pytest tests/unit/scripts --collect-only` → 3 tests（原先 0）。
- 全量 `tests/unit`：737（基线）→ **752 passed**，0 failed。
  拆账：+3 恢复采集（`tests/unit/scripts/`）+ 9 观测口径层 + 3 本轮空壳线回落 = 752。

### F. 教训

- **"测试目录存在"不等于"测试在跑"**：pytest 不会告诉你某个目录被配置排除了。
  想知道采集面，唯一的办法是 `--collect-only` 看数量。
- **写死的魔数断言会腐烂**：因为没人跑，它还能烂着；
  改成从源数据推导条数，腐烂就变成"源数据变了，断言跟着变"。
- 排除规则按 basename 匹配 → 目录名取个通用词（`scripts`/`tests`/`utils`）
  会在**任何层级**误伤。改排除规则前先 `--collect-only` 存一份基线。

## 12.33 重建路径的**静默降级**守卫（ledger 有成交 + holdings 缺失 → 拒绝重建，2026-11-02）

### A. 触发

§12.32 治理的是"**展示层**把事实读反"；本条治的是"**重建路径**把数据残缺
悄悄降级成没发生过"。两者同源：**静默降级比报错更贵**。

### B. 根因（机制级，不是猜）

`load_holdings()` 在 holdings 文件**不存在**时返回**空壳**：
`{cash: capital, positions: {}, initial_capital: capital}`。
而重建路径 `rebuild_line_from_files()` 直接用它 → 一条
「ledger 里明明有 60 笔成交、只是 holdings 文件丢了」的线，
会被重建为 `cash=100万 / 0 持仓` → 在 `portfolio.json` 里变成
**"未建仓"** → 前端读起来像**"这条线从没做过"**。

关键难点：**"holdings 文件不存在"有两种性质完全不同的情况**

| 情况 | 判定 | 该怎么办 |
|---|---|---|
| ledger 也没有成交 | 合法空壳（`multi_asset_final` 至今的真实状态） | 正常重建为空壳 |
| ledger **有**成交 | **数据残缺**（持仓文件丢了） | **拒绝重建**，保留旧值 + 告警 |

不区分这两者，就必然会误伤合法空壳，或者放过数据残缺 —— 二者必居其一。

### C. 修法（守卫，只挡降级、不改口径）

在 `rebuild_line_from_files()` 开头加判据：
**holdings 文件缺失 且 `ledger_stats(strategy)["n_trades"] > 0` → 抛 `RuntimeError`**。
上层 main 循环已有的 `except` 会打印告警并**保留 `portfolio.json` 里的旧值**，
ledger / 其它文件一概不动（可人工从 ledger 恢复）。

- 不改任何字段口径、不改展示层、不改交易逻辑；
- 合法空壳照旧能重建（`multi_asset_final` 不受影响）；
- 守卫触发时**不写任何文件**（有测试锁死）。

### D. 验证

- 门禁：`tests/unit/trading/test_paper_rebuild_guard.py`（5 条）——
  ①ledger 有成交+holdings 缺失 → 抛异常且消息含笔数/文件名；
  ②ledger 不存在 → 合法空壳照常重建（value=100 万，**不是 0**）；
  ③ledger 只有表头 → 不拦；
  ④holdings 存在 → 一律正常重建（守卫不误伤）；
  ⑤守卫触发时 ledger 内容不变、holdings 不被凭空造出。
- **真实数据体检**（7 条线逐条判定，无一误触发）：

  | 线 | holdings | ledger 笔数 | 守卫判定 |
  |---|---|---|---|
  | 22f | 有 | 60 | 不触发 |
  | honest_42f | 有 | 140 | 不触发 |
  | rsi_71421 | 有 | 60 | 不触发 |
  | factor_ranking | 有 | 87 | 不触发 |
  | gbm_voltgt | 有 | 24 | 不触发 |
  | honest_42f_neu | 有 | 58 | 不触发 |
  | multi_asset_final | 无 | 0 | 不触发（合法空壳） |

- 门禁 d：全量 `tests/unit` 通过（752 + 5 = 757）。

### E. 教训

- **"文件不存在"要先分清是"没发生过"还是"丢了"**，再决定回落还是报错；
  回落（fallback）是最容易埋雷的写法。
- 守卫要有**反向测试**：不只测"该拦的拦住了"，还要测"不该拦的没被拦"
  （合法空壳）——否则守卫会变成新的静默故障源。

## 12.34 纸面盘**三档排期并发写账本**（加进程互斥锁 + 单一责任源，2026-11-02）

### A. 触发

18:10 的首跑复盘任务核查 17:40 那次触发时，从日志时间戳里发现

### D. 修法

1. **进程互斥锁**（根治并发）：`paper_portfolio.py::acquire_run_lock()`，

   语义是**等待，不是跳过** —— 若后来的实例直接跳过，前面那个漏掉的线就永远

   （周一 17:40 + 周二 09:20 兜底）；`signal_quality.py` 跟着搬到
   `weekly_paper_portfolio.sh` 里、**排在纸面盘之后**（它读 ledger 里的成交记录，
   必须排在调仓后面才统计得到当次成交）。
   → 顺带消掉 16:05 那次"注定失败"的 exit 3 噪音。

### E. 门禁

- `tests/unit/trading/test_paper_run_lock.py`（4 条）：无竞争可拿锁 /
  超时 exit 75 / **别人持锁时会等到对方释放**（核心语义）/ 锁路径随 `PAPER_DIR`。
- 真实路径验证（真实 `data/paper/`）：子进程持锁 3s → 主实例打印
  「⏳ 另有纸面盘实例正在跑…」→ **3.2s 后拿到锁** ✓。

### F. 教训

- **"多档排期 = 容错"有另一面：多档排期 = 多档并发写**。今晚它表现为
  "17:40 那次补上了 17:30 那次漏的"，看着像容错；但那只是**运气**。
- 排期设计不能只看"谁负责跑"，还要看"**同一时刻可能有几个在跑**"。
- 退出码要能被解释：`exit 3` 一度像故障，实际是"时点早于数据落地"的结构性必然
  —— 这种"注定失败"的排期档位本身就是设计缺陷（它污染 launchctl 的健康信号）。

**multi_asset_final 当晚显示的 "-0.10%" 其实是手续费损耗，不含任何市场波动**。

### B. 三个 bug 叠在一起（全部实测定位，非推测）

| # | 位置 | 现象 | 根因 |
|---|---|---|---|
| ① | `paper_portfolio.py::_record_buy` | 新建仓的 `adj_cost` 是 **NaN** | 取的是 `adj_close.at[latest, c]`，`latest` 是**信号日**不是成交日；信号日该票没有后复权价 → NaN |
| ② | 同上 | NaN 被写进持仓文件 | `round(a_cost, 6) if a_cost else None` —— **NaN 是 truthy** → 走 round 分支 → NaN 落盘 |
| ③ | `paper_portfolio.py` 回填段 | NaN 永远修不好 | `if _pos.get("adj_cost"): continue` —— **NaN 是 truthy** → 永远跳过回填 |

后果链：`adj_cost=NaN` → `_adj_ratio` 因 `not np.isfinite(a_cost)` **恒返回 1.0**
→ **该票市值 = 买入金额，永不随市价波动** → 组合净值只反映手续费。
实测 2026-11-02 首跑：**multi_asset_final 69/69 只**、其余各线 3~12 只中招。

### C. 为什么今天才暴露

今天 11-02 是**这些线第一次真的建仓成功**（此前一直失败/未建仓）。
而更底层的成因是数据管道：
`load_adjusted_close` 用**交易所口径涨跌幅**合成后复权价，
当日涨跌幅要等 baostock(T+1) 或 TDX raw 包 —— 17:30 那次跑的日志里
`sync_pct_chg from TDX` 报「**没有可用的 TDX raw 分区**」
→ **adj_close 最后一行整行 NaN** → ①必然触发。

### D. 修法（口径收口到一个函数）

新增模块级 `last_valid_adj(adj_close, code, as_of)` →
取 **≤ as_of 的最后一个有效后复权价**（方案书 §2.2 的 last_valid_close 兜底；
停牌期价格本就不变，语义正确）。
**四处统一用它**：① 买入成本 ② adj_cost 回填 ③ 组合估值的分子 ④ 一次性修复脚本。
同时：
- `adj_cost` 分子改用**成交日**（原来用信号日 → 净值滞后一个交易日）；
- `buy_date` 改记**成交日**（原来记信号日）；
- 两个 truthy 判断改成"是否有效"（非空且有限）；
- 回填的日期以 **ledger 的成交日**为准（`ledger_buy_dates()`，ledger 权威）。

### F. 教训（本项目第 N 次同款）

- **NaN 是 truthy**：`if x:` 判空对 NaN 无效 → 用 `is not None and isfinite(...)`。
  这已经是本项目**第三次**栽在"判空用 truthy"上（§12.31 的 tests/unit/scripts、
  §12.32 的 `cash=0`/`value=0` 被 `or` 吞掉、这次）。
- **"数字看起来合理"不是验证**：multi_asset_final 当晚显示 -0.10%，
  看起来就是个"小亏"，实际是**完全没有市场暴露**。
  → 判据要问"这个数字**能不能**由它声称的机制产生"。
- **兜底不能是"静默冻结"**：ratio 兜底成 1.0 看起来"合理"（停牌价格不变），
  但在"涨跌幅没同步"的情况下它把**整个持仓的波动抹掉了**。
  → 兜底必须**打标记**（stale_price / price_date），让下游知道用的是旧价。

## 12.36 纸面盘**日频盯市**（nav_daily）+ 门禁 a 的第一次实战

### A. 为什么做

周频 `nav_history` **一个季度只有 12 个点** → 年化波动/夏普**没有统计效力**
（波动要靠 252 个点估）。方案书正文 §1 方案 A：每个交易日一个点（约 240 点/年）。

### B. 实现要点（口径纪律优先）

| 决策 | 做法 | 理由 |
|---|---|---|
| 估值 | 调 `paper_portfolio.total_return_portfolio_value()` | 周频/日频**同一份代码**，不复制公式 |
| 持仓 | 从 `ledger.csv` **逐笔重放** | 周频每 7 天才调仓，日频要每天的持仓 |
| 现金 | 重放时**自算**（佣金万3/最低5 + 印花万5 + 滑点千1） | ledger 的 `cash_after` **只在当日首行有值**，11-02 的行全空 → 不可依赖 |
| 卖出所得 | 用 ledger 的 `amount`（= 总回报口径成交额） | 与 `paper_portfolio.run_line` 的 sells 同源 |
| 落盘 | 独立文件 `data/paper/<strategy>_nav_daily.json` | 语义不同 + 避免与周频抢写同一文件 |
| 起点 | **首次建仓日** | 建仓前不该出现"0 收益点"（会把波动算低） |
| 幂等 | 按 date upsert + 排序 | 断点续跑 = 一次跑完 |

### C. 门禁 a 抓到了真东西（不是走过场）

第一次跑完，日频末点与周频末点**差 5,239 元**（22f）。
逐项对账后发现：重放的**现金**与真实持仓差一大截 →
根因是 ledger 的 `cash_after` 字段在 11-02 的成交行里**全部为空**
（写入时没填），而我最初的重放器把它当权威。
→ 改成自算现金（与 `paper_portfolio` 成本模型逐项一致），
   卖出侧改用 ledger 的 `amount`（总回报口径成交额，账本里就是它）。
→ 差额 5,239 → 844 元（gbm_voltgt 已到 0.01）。
→ 再查是 `adj_cost` 的**信号日/成交日错位**（建仓时按信号日写下，回填时因
   "旧值有效"被跳过）→ 按成交日无条件重算 → **6 条线全部逐位对上**（≤0.02 元）。

**这正是门禁存在的意义**：日频和周频是两条独立实现，
如果不做逐位比对，口径漂移会静默地写进用户的净值曲线。

### C2. 门禁 a 追出的**第三个**日期错位（信号日 vs 成交日）

第一轮把现金改对后，残差从 5,239 降到 **300~850 元**（gbm_voltgt 已到 0.01）。
逐项比对 `adj_cost` 才发现：
- 建仓当时写下的 `adj_cost` 用的是**信号日**的后复权价（那是旧 bug 的写法），
- 而分子（估值日）是成交日 → **分子分母落在不同日期** → 收益失真；
- fix 脚本原来只在 `adj_cost` 为 NaN 时回填 → **已有值但日期错位的那些票被跳过**。

→ 改为**按成交日无条件重算**，并记 `adj_cost_date`；
`paper_portfolio.py` 的回填跳过条件也从"值是否有效"改成
"**价格日是否就是成交日**"。

**教训串起来看**：同一条线上连续踩了三个"日期/判空"坑——
① truthy 判空（NaN 是 truthy）② 信号日 vs 成交日 ③ cash_after 字段缺失。
**它们叠加后的表现是"数字看起来正常"**（-0.10%、+0.12%），必须靠
"同一指标两条独立实现逐位对账"才能抓到 —— 这就是门禁 a 的价值。

- `scripts/daily_nav.sh` → Hermes cron `0294eb16149f`「纸面盘日频盯市」
  **交易日 18:20**（等纸面盘 flock 释放后再跑，最多等 40 分钟）。
- 推送 `daily-signal-push` 从 **18:00 → 18:30**（等日频净值写完再推）。

### E. 已知限制（写下来，别忘）

  绩效评估仍用周频 `nav_history`（每周追加、不可重算）。

  两套口径拼接，混进同一条曲线会引入不可解释的差异。
